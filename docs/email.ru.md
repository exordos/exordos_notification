# Почтовые события с авторизацией

[English version](email.md)

Все POST и GET для событий требуют действующий IAM-токен, включая почтовые
события подтверждения регистрации Core. API v1 защищён штатным IAM middleware;
обхода авторизации при вложенном обращении к EventType нет. Отправителю нужны
права `exordos_notification.event_type_<TYPE_UUID>.create/read`.
Требуются и доступ к каталогу, и разрешение на источник/тип события.
Отправитель с правами только на чтение не может изменять или удалять события.
Управляющий CRUD использует штатные IAM-контроллеры с областью проекта;
обычные авторизованные пользователи могут читать опубликованные записи каталога.

Элемент `notification_email` предоставляет общий SMTP-провайдер и настройки
отправителя. Он не настраивает Core или другие приложения и не устанавливает
специфичные для них типы событий и шаблоны писем.

Чтобы включить почтовые события Core, установите `core_notification_email`
из репозитория Core. Его зависимости подтягивают `notification_email`,
который зависит от базового сервиса Notification и mailaas. Core владеет
типами событий регистрации и сброса пароля, шаблонами писем, служебной учётной
записью и конфигурацией отправителя.

Элемент Core следует существующему подходу манифестов `metapaas_audit`
и `ecosystem_audit`: создаёт IAM-пользователя с `type: service`, правами
create/read для типов регистрации и сброса пароля и правом чтения каталога,
а также ресурс `$core.iam.tokens` с `auto_renew: true`. Значение `:access_token`
попадает в отдельный файл конфигурации событий Core с правами `0600`
как параметр `exordos_api_token`.

Штатная служба Core обновляет токен до истечения половины срока его действия.
При изменении токена сверка конфигурации перезаписывает его файл и перезапускает
только `ec-gservice`. Существующий отправитель SDK читает новый токен для отправки
событий и запросов статуса. Установка или изменение статической конфигурации
асинхронного клиента и соответствия типов событий перезапускают `ec-user-api`;
обновление токена не прерывает Core API. Если необходимые файлы ещё отсутствуют,
действие обновления токена пропускается. Ошибка перезапуска отправителя остаётся
ошибкой для агента конфигурации. Вход по паролю, отдельный протокол обновления
токена и новая реализация авторизации в SDK/Core не нужны.
Сохраняйте `client_type = async`: при регистрации событие записывается локально,
а существующая служба отправителя доставляет его асинхронно.

В существующих установках сохраните действующие почтовые ресурсы и изменённые
шаблоны до переноса владения элементами и импортов. Не устанавливайте вторую
копию того же типа события и не удаляйте работающий SMTP-релей ради перехода
на новую схему владения.

В первоначальной версии 2.0.0 почтовый элемент также владел конфигурацией
отправителя Core и типом события, а конфигурация инсталляции — шаблоном
подтверждения. Переход на `core_notification_email` передаёт эти ресурсы Core.
Сохраняйте действующие токены, типы событий и изменённые шаблоны до переноса
владения. Не устанавливайте дублирующие ресурсы и не удаляйте работающий транспорт.

До развёртывания обязательной авторизации Notification подготовьте управляемый
токен и проверьте доставку его конфигурации. Сохраните UUID почтового EventType
и существующий формат v1. Проверьте настоящую регистрацию Core по всей цепочке:
очередь событий, авторизованные POST/GET Notification и SMTP. На тестовом токене
с коротким сроком действия вызовите обновление и проверьте замену конфигурации,
перезапуск отправителя, сохранение процесса User API и успешную отправку
с новым токеном. Принятие запроса API само по себе не доказывает доставку письма.
